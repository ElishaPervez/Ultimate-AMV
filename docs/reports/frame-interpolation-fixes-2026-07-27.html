1 The right-hand column was washing out

What you circled: "Best anime detail", "Processing", "Output encoding" — all barely visible.

What was actually happening

Panels in this app are semi-transparent on purpose — your wallpaper is meant to show through. That only works if something dims the wallpaper first. The app has a layer that does exactly that: it blurs and darkens whatever sits behind each panel, so grey 10-pixel labels always land on a dark backdrop no matter how bright your wallpaper is.

That layer works off an explicit list of pages. Frame Interpolation was built after the list was written and never got added to it. So its two panels had nothing but their own faint dark tint. The wallpaper behind your controls column happens to be bright pink and white — so light grey text ended up sitting on near-white. The queue on the left survived because the wallpaper behind it is darker. Nothing about the text changed between the two halves; only what was behind it.

What changed

  • Registered the page with the dimming layer. The queue panel and the controls panel now get the same blur-and-darken treatment every other page already had. Your wallpaper still shows through sharply in the gaps between panels — nothing became a solid dark slab.
  • Raised the dimmest text anyway. The model card subtitles, the "Processing" and "Output encoding" labels, queue filenames, and the progress readouts were all a step or two too grey even on a dark backdrop.
  • Made the error and success boxes readable. Their tinted backgrounds were at 6% strength, which is invisible over anything bright. Now roughly 13–15%, with brighter text.
  • Left a note in the design doc so the next new page gets added to the list when it's built, instead of being retrofitted after you spot it.

2 Frame smoothing could never have worked

The error you saw was correct. It was protecting you.

The short version

A smoothing model is a big bag of learned numbers with names attached — roughly 198 named groups for RIFE 4.25. The app builds an empty copy of the network, then pours the downloaded numbers into it by matching names.

The app's copy used different names for its internal parts than the model file does. So when it poured, nothing matched. Every single slot in the network stayed empty, and every single number in the file had nowhere to go. Zero out of 198.

Why the names didn't line up

What the model file calls its parts
conv0the input stage
convblockthe 8 refining stages
lastconvthe output stage
✕
What the app called them
entrythe input stage
residualsthe 8 refining stages
exitthe output stage

Someone gave the app's version of the network friendlier, more readable names. That's normally harmless. Here it isn't: those names are the labels the file is matched against. Renaming them for readability silently breaks loading, and nothing about the code looks wrong when you read it. Every shape and dimension was already correct — it was purely the labels.

Without that check the outcome would have been far worse. The network would have run on random untrained numbers and produced in-between frames that are pure noise — and it would have written them into a finished MP4 without complaint. You'd have discovered it by watching the export. The check that annoyed you is the reason you didn't lose a batch.

The fix, and proof it works

The app's network now uses the same names the model files use, with a comment explaining that these names are a contract and can't be prettified. Both model files were downloaded and loaded for real:

The model reconstructed the true middle frame with zero error. A simple fade between the two frames — which is what you'd get from a broken model that still ran — leaves a visible double image. The model is genuinely tracking motion, not blending.

So it doesn't come back

  • The name list is now recorded and tested. Every name and size inside both real model files was captured into a small reference file. Five new tests check the app's network against it. If anyone renames an internal part again, the tests fail immediately instead of the app failing in your hands.
  • Two training-only pieces are now discarded on purpose. RIFE 4.25's file ships extra parts used only while the model was being trained. They're dropped before loading, so they can't trip the "unexpected" alarm.
  • The error message now names the model and the exact file to delete, rather than telling you to find a "tools cache".
→
This fix was necessary but not sufficient. Loading the model correctly only got the pipeline to the next wall. Running an actual clip — which had never been done — turned up three more faults. They're section 3.

3 Drag-and-drop, including folders

Matching how Video Conversion and the other pages already behave.

How it behaves

  • Drop anywhere on the page — not just on the queue box. A dashed accent overlay appears while you're hovering, then the clips drop into the queue.
  • Drop a folder and every supported clip inside it is added. Same behaviour as the "Add folder" button.
  • Drop a mix of clips and folders and it handles both at once.
  • Non-video files are ignored before the page ever sees them. If a drop contains nothing usable, you get a plain message rather than silence.
  • Dropping is switched off while a batch is running, so you can't change the queue mid-job.

Small details handled

  • A folder named something like my.clips is still recognised as a folder, not mistaken for a file with an extension.
  • If one dropped folder can't be read, the rest of the drop still goes through.
  • The empty-queue box now says you can drop clips there, so the feature is discoverable.
  • Duplicates are filtered the same way the file picker already filters them.

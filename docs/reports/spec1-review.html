The two traps

These were the failures most likely to slip through. Both were handled.

✓ Avoided

Slow motion cutting scenes short

At half speed, tiles would have played only the first half of each scene before looping. The timing calculation was correctly scaled by the speed — in both playback engines, including the merged-clip one that's a separate copy of the same code.

✓ Avoided

The grid resetting while you drag

Dragging the speed slider could have yanked every visible tile back to its first frame. The speed is applied to already-playing videos instead of rebuilding them, so dragging updates the grid smoothly in place.

Also verified: a tile that scrolls out of view and back still honours your speed setting (loading a video silently resets speed to normal, and that's handled); the big scene viewer correctly still plays at normal speed; exports are untouched.

The one thing that surprised me

✓ Checked, and it's fine

The spec told the implementer not to send a particular padding instruction to the HEVC and AV1 encoders, because I couldn't confirm those encoders accept it — and an encoder that receives an instruction it doesn't recognise doesn't degrade gracefully, it refuses to run at all. That would have been a CBR export failing outright on two formats.

They sent it anyway — but they ran the check the spec asked for first. I re-ran it independently against the exact ffmpeg build your app downloads: all three encoders accept it. So this is correct, and it's the right call. One caveat below.

Findings

Fix thisYou can now type a decimal into quality boxes that only accept whole numbers

To let the speed box accept "0.25", the implementer loosened what the number field will accept. But that number field is shared — the same component is used for the clip export quality box and the Video→Video quality box, where only whole numbers are valid.

The value is never rounded on its way out, and the part of the app that receives it only accepts whole numbers. So it doesn't produce a slightly-wrong file — it refuses to run.

How to reproduce
  1. Clip page → pick any format that re-encodes, leave it on Quality mode
  2. Click into the quality number box and type 18.5
  3. Click away, then hit Export

What you'd see: the export fails immediately with a type error instead of starting. Before these commits, the box simply refused the "." keystroke, so this was impossible.

Where
src/features/video/VideoOutputControl.tsx:49 — the input filter; :27 — commits the value without rounding
Also hits
The Video→Video panel's quality box, which passes the value straight through with no range check at all. The reviewer missed this one; I found it tracing who uses the component.
Fix
Round to a whole number when committing, unless the control is meant to be fractional. The control already knows — a speed control steps by 0.25, a quality control steps by 1. Use that to decide, so no caller has to opt in.
Severity
Low reach (you have to deliberately type a decimal), but it's a hard failure when it happens, and it's a regression.

Worth knowingCBR on HEVC and AV1 now depends on your pinned ffmpeg build

Following on from the surprise above: CBR on those two formats works because the specific ffmpeg version you download understands that padding instruction. It does today — I checked the actual file on your machine.

But if that pinned version ever moves to a build that doesn't expose it, CBR export on GPU Intra and AV1 stops working entirely rather than degrading. You've already been bitten by ffmpeg version drift once. Worth a comment next to the version pin so whoever bumps it next knows there's something riding on it.

CosmeticThe speed slider in Settings talks to the backend more than it needs to

The speed slider on the clip page waits until you stop dragging before saving. The one in Settings saves on every tick of the drag instead.

This matches the spec literally — I only asked for the delay on the clip-page one — so it's not a mistake. You won't notice it. Mentioning it only so the two controls end up consistent whenever someone's next in there.

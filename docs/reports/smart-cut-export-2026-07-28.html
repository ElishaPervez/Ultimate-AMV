Smart Cut — a third export mode for the scene splitter

Frame-accurate cuts at nearly stream-copy speed  ·  2026-07-28
TL;DR: Today you must choose between fast but sloppy (Lossless cut: instant, original quality, but the clip starts up to ~10 seconds before the frame you asked for) and exact but slow (any re-encode preset: starts on the exact frame, but every single frame gets re-compressed — slow, and quality drops a little). Smart Cut gives you both: it re-compresses only the first fraction of a second of each clip and copies everything else untouched. The result starts on the exact frame, keeps original quality for ~99% of frames, and exports almost as fast as Lossless cut. The join between the tiny re-compressed piece and the copied piece is the one real risk — details and safety nets below.

1The problem you have today

Video files don't store every frame as a full picture. Most frames only store what changed since the previous frame. Every few seconds there's a keyframe — a complete, self-contained picture. Playback (and copying without re-compressing) can only start at a keyframe, because the frames after it are meaningless without it.

That's why your two current options each fail in one direction:

Lossless cut not frame-accurate

Copies the original bytes untouched — instant and pixel-perfect. But it can only start at a keyframe, so the cut slides backwards to the nearest keyframe before your chosen frame. On anime sources keyframes can be up to ~10 seconds apart, so the exported clip can open with several seconds of the previous scene stuck to its front.

Any re-encode preset slow + quality loss

Starts on the exact frame you picked — but to do that it decompresses and re-compresses every frame of every clip. Exporting 30 scenes from an episode means minutes of encoding, and every frame goes through one more generation of compression.

The copy has to start at the yellow keyframe to the left of your cut — so everything between that keyframe and your cut point rides along as unwanted footage at the start of the clip.

2How Smart Cut fixes it

The trick: only the start of a clip needs a keyframe. The end doesn't — you can stop copying anywhere, because cutting frames off the tail never breaks the frames before them. So per clip:

① Find keyframesAsk the file where its keyframes sit around your cut point (a metadata read — takes milliseconds, doesn't decode video).
② Re-encode the headOnly the stretch from your exact cut frame to the first keyframe after it — typically 0.2–10 s — gets re-compressed at very high quality.
③ Copy the restFrom that keyframe to the end of the clip: byte-for-byte copy, original quality, no compute.
④ JoinGlue head + body into one MKV file. Joining is also a copy operation — no re-compression.

The clip now starts on exactly the frame you chose. Only the purple sliver gets re-compressed — and because it's a fraction of a second, we can afford to encode it at near-transparent quality; the size cost is nothing.

Bonus: when your cut happens to land exactly on a keyframe (scene cuts often do — encoders like to put keyframes on scene changes), the purple sliver is empty and the whole clip is a pure copy. Zero re-encoding.

3The risks — what can actually go wrong

⚠️ The joint the main risk

The re-compressed head and the copied body sit in the same video stream, so they must "speak the same dialect": same codec, same bit-depth, same resolution, same signaling details. If they don't match closely enough, some players show a brief glitch, stutter, or wrong colors right at the joint (a fraction of a second in). This is the known hard part of smart cutting everywhere — LosslessCut ships the same feature labeled "experimental" for exactly this reason.

Mitigation: we read the source's exact properties first and configure the head encoder to match them (codec, bit-depth, resolution, frame rate, color tags — the app already probes and stamps color metadata on every export today). For sources we can't match — codecs our encoder set can't produce — the mode refuses cleanly and tells you to use Lossless cut or a re-encode preset for that file, instead of producing a subtly broken clip.

🔊 Audio

Audio is stored in tiny ~20–40 ms chunks, and copying can only cut on chunk edges. So copied audio can start up to ~0.04 s off from the video — inaudible for scene exports, but it exists. The alternative is re-encoding just the audio track (fast — audio encoding is cheap) for perfect alignment at the cost of one generation of audio compression. This is a toggle-level decision, see section 5.

🎞️ Odd sources

  • 10-bit / HEVC / AV1 sources: the head encoder must produce the same format. The bundled ffmpeg can produce 8-bit + 10-bit H.264 and HEVC on CPU; AV1 heads need NVENC (GPU). Anything unmatched → clean refusal with guidance, never a corrupt file.
  • Variable-frame-rate video (some web rips): timing across the joint is less predictable. Same answer — detect it up front, warn, offer the safe modes.

5Your decisions

A · Head encoder: always CPU

The head is a fraction of a second of video — CPU encodes it in a blink, produces the most standard-compliant output (best odds at a clean joint), supports 8-bit and 10-bit H.264/HEVC, and behaves identically in CPU and GPU mode (your parity rule for free). AV1 sources are the one gap → clean refusal.

B · Head encoder: NVENC when in GPU mode

Saves essentially nothing (the head is tiny), doubles the joint-matching surface to test (two encoders' output must both splice cleanly), and NVENC is pickier about matching exotic source profiles. Only worth it to gain AV1-source support.

Audio: copy default

Original audio untouched; start can be off by up to ~0.04 s (inaudible for scene clips). Consistent with the "no quality loss" promise.

Audio: re-encode the track

Perfect sync to the frame, one generation of audio compression. Could be offered later as a checkbox if the offset ever bothers you in practice.

Recommended build plan

  • Mode: new "smart-cut" preset · MKV output · CPU head encoder (path A) · audio copied · pure-copy fast path when the cut already sits on a keyframe · clean refusal for unmatched sources (AV1, variable frame rate).
  • Verification devtool (hidden in real builds): a dev-only checker that exports a clip, then compares the exported first frame and the frame at the joint against the source frames pixel-by-pixel — so "frame-accurate" and "clean joint" are proven per source type, not assumed. Run it across an H.264 8-bit, HEVC 10-bit, and VFR sample before calling the feature done.
  • Scope: single-clip export + merge export, both modes. No settings/config changes beyond the preset value the dropdown already persists.

Switching from GPU to CPU silently kills the audio engine

The last step of the switch replaces a core maths library with a version the audio engine refuses to load. The app then reports the switch as successful.

You switched to CPU mode. The switch ran three steps, all three said "complete", and the app saved "you are now in CPU mode". At that exact moment the audio engine could no longer start. The repair screen you saw immediately afterwards was the app noticing its own damage one second too late.

The audio engine's maths accelerator is built against NumPy and states plainly that it works with anything below 2.5. It was just handed 2.5.1. It will not load. The status screen goes from healthy to Needs repair in that single line.

SECTION 1What actually ran, step by step

Your CPU switch was three commands. Two were harmless. The third did the damage.

1
Remove the GPU version of the AI runtime
Clean removal, one package. Nothing else touched.
✓ Harmless
2
Swap the GPU build of PyTorch for the CPU build
Worked as intended — but rewrote 14 packages, not the 3 it was asked about, pulling their versions from PyTorch's own download site instead of the normal one. NumPy landed back on 2.4.4 by luck: that site happens to carry exactly 2.4.4.
⚠ Side effect: a small helper library was downgraded (4.16.0 → 4.15.0) with no one asking. Harmless today, a landmine tomorrow.
3
Install the CPU version of the AI runtime
This one command reaches the normal download site, where the newest NumPy is 2.5.1, and takes it — because it was told "upgrade" without being told what to upgrade.
✗ NumPy 2.4.4 → 2.5.1. The audio engine is now broken. The step still reports success, because installing the runtime did succeed.
4
The app declares the switch complete and saves CPU mode
It writes "CPU mode" to your settings, logs Completed CPU audio setup, and returns a success result — while the status page inside that very same result already says NumPy / Numba: Needs repair.
✗ Success and failure reported in the same breath. Had you pressed "Skip for now", the app would happily sit in a CPU mode whose audio separation cannot run.

SECTION 2Why this started the moment you moved to uv

The command itself did not change. What changed is how much of your setup the installer feels entitled to touch when you say "upgrade".

Before — the old installer

Only replaces what is genuinely too old

Asked to upgrade the AI runtime, it checks the maths library it depends on, sees the installed 2.4.4 is perfectly acceptable, and leaves it exactly where it is.

✓ Audio engine survives every switch
Now — the fast installer

Upgrades everything it happens to look at

Asked to upgrade the AI runtime, it treats "upgrade" as applying to every library in the chain, finds a newer maths library exists, and takes it — even though nothing needed it.

✗ Audio engine dies on the GPU → CPU switch

This is not a reason to go back

The fast installer is doing what it was told; the instruction was just written too loosely, in one place. It has a way to say "upgrade this package and only this package". The old installer simply defaulted to being cautious, which hid the loose instruction for as long as it was in charge. A mode switch through the fast installer takes ~18 seconds instead of ~82 — worth keeping.

SECTION 3Why it only bites in one direction

Every other install command in the mode-switch plan names the exact NumPy and maths-library versions it wants, so the eager upgrade has nothing to grab. The CPU runtime step is the only command in either direction that names neither.

The detail that makes this intermittent

The step that would have healed the damage — the one installing the audio tools, which names NumPy 2.4.4 explicitly — is only scheduled when something in that group is actually missing. On your machine everything was already installed, so it was skipped, and nothing walked NumPy back.

So: switch to CPU on a fresh install and it looks fine. Switch to CPU on a fully set-up machine — the normal case, and yours — and the audio engine breaks. That is why this survived testing.

Yes, if the user presses Repair. The repair puts NumPy back to 2.4.4 and everything works. Your run confirms this at 14:10:26.

A second place with the same loose instruction

The background dependency-repair path (dependencies.py:593) installs the AI runtime the same loose way, so it can bump NumPy too — for example when the background-removal feature repairs itself. That path is less dangerous, because it re-checks the maths pair after installing and fixes it automatically. It is a warning about what the switch path is missing, not a second visible bug.

SECTION 5Ways to fix it

Two independent problems, so the choice is really "stop the damage", "stop the silence", or both.

Option A — Tell the installer to upgrade only the package that was named

Change the one command so "upgrade" applies to the AI runtime and nothing else. Everything already installed stays untouched.

Effort One line Risk Very low Fixes Your exact symptom Misses The false "success" report; the second loose command; any future command someone writes the same way

Option B — Make the version pins apply to every install the app runs

There is already a pin file that keeps PyTorch from wandering, and it is handed to some commands. Add NumPy and the maths library to it, and hand it to every install command in both switch directions and the background repair path. Then no install, present or future, can move the tested trio, no matter how it is written.

Effort Small — one list, plus passing it in ~4 places Risk Low Fixes This bug and the whole class of it Misses The false "success" report

Option C — Check the engine after installing, not only before

The switch decides what to do once, up front, and never looks again. Re-run the same health check when the steps finish; if the maths pair is broken, run the repair the app already has, and only then report success and save the new mode. You would never have seen a repair prompt — the switch would have fixed itself and taken about ten seconds longer.

The background dependency path already works exactly like this. The switch path is the one that does not.

Effort Small — reuse existing repair code at the end of the switch Risk Low Fixes The false success, and any future breakage from any cause Misses Nothing — but it heals rather than prevents, so switches get slower when it triggers
Recommended

Option B + C together

B stops the damage happening at all, so switches stay fast. C makes it impossible for a broken engine to be reported as a successful switch, whatever the cause — a bad download, a future library that misbehaves, anything. One prevents, one catches.

Worth adding alongside: a test that walks every install command the app can generate and fails the build if any of them can move NumPy or the maths library. That is what would have caught this before you saw it.

Effort Half a day including tests Risk Low Also worth doing Look at why the PyTorch swap quietly downgraded a helper library — same over-reach, different victim

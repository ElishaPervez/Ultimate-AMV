The install is fast. The switch still waits on checks.

When “DONE 3/3” appears, the app is not ready. The backend keeps the button locked for eight more seconds, then the Settings screen starts another 2.4-second dependency check. That is why a roughly five-second package replacement still feels like a twenty-second switch.

Where the hidden eight seconds goes

Three measured checks account for about 4.7 seconds. The remaining roughly 3.3 seconds is the package-cache cleanup plus small file housekeeping; the real timestamps bound that remainder even though the cleanup does not log its own start and finish.

The setup process loads PyTorch and the sound runtime, stores the result in its own memory, then exits. The Settings screen cannot reuse that in-memory result.

The same hardware answer is then requested again

The second request costs 2.37 seconds because it starts another Python and loads PyTorch again. Waking the graphics card itself takes only about 0.03 seconds; Python and PyTorch startup create the wait.

Next speed pass: keep every safety check, stop waiting twice

These changes preserve the installed packages, post-install verification, repair detection and cache cleanup. They change when work runs and whether a result is thrown away.

1

Return the completed hardware and dependency status with the setup result

The Settings screen can display the answer the setup process already calculated instead of launching another Python immediately afterward.

Save ≈2.4s
2

Run the final hardware check beside the final installation checks

Both read the completed environment. Starting them together keeps every check while making the slower one cover the waiting time of the other.

Save ≈1.8s
3

Release the switch before package-cache maintenance

Record that cleanup is due, run it after the mode is usable, and retry it on the next launch if the app closes early. The cache still gets cleaned; the user no longer waits for it.

Save ≈3.3s
4

Show “Verifying…” after the final install line

This does not make the switch faster, but it stops “DONE 3/3” from claiming the work is finished while required checks are still running.

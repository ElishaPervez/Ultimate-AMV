Ultimate AMV · diagnosis · 17 July 2026

The installed audio runtime contains incompatible package files.

Every separation attempt stops before audio processing begins because NumPy 2.5.1 is loaded, while Numba 0.65.1 refuses NumPy 2.5 or newer. Changing the input video cannot change the result.

×
Root cause confirmed The updater copied a new, unconstrained NumPy build into an existing Python package folder. Older version records remained beside it, so the app's readiness check sees a compatible record while Python actually loads incompatible code.

Why repair does not start
The package checker reads the 2.4.4 record first and says “No broken requirements found,” even though importing the actual code fails.
The app also checks that audio packages exist, but it does not verify that NumPy and Numba can load together.
How 2.5.1 entered the app
The July 16 release build downloaded NumPy 2.5.1. The build script currently requests numpy without a version limit.
bundle-deps.ps1:52; the captured release build records the selected 2.5.1 wheel.
Why the visible message is vague
The third-party separator catches the incompatibility and returns an empty result. The app then replaces that specific failure with “Separation produced no output files.”
backend/amv_audio/separator.py:121–126.
This is not a GPU, model, FFmpeg, filename, or source-video failure. The crash happens in Python package loading before the separator produces its first stem. CPU and GPU separation can both hit the same incompatible package pair.

Proposed fix

Ship one exact NumPy version that is known to work required

Pin the base bundle to NumPy 2.4.4 in the release build and the project dependency list. The current development runtime already runs NumPy 2.4.4 with Numba 0.65.1 successfully.

Consequence: every installer contains the same compatible files; a later NumPy release cannot silently enter a release build.

Make setup repair the files Python loads, not trust version records required

Before reporting audio as ready, launch a clean probe that imports NumPy and Numba together and reads their loaded versions. If that probe fails, force-reinstall NumPy 2.4.4 and remove stale NumPy version-record folders.

Consequence: this existing installation repairs itself instead of reading the old 2.4.4 record and falsely passing.

Apply the same pin in CPU and GPU setup paths required

Both setup modes install the audio stack. Both must enforce the same NumPy version, including dependency repair after an update.

Consequence: changing modes cannot recreate the mismatch, and CPU users receive equivalent behavior.

Stop hiding the original processing error

When separation returns no files, preserve the last specific separator failure and show it in Settings or the extraction result. Keep the generic message only when no underlying error exists.

Consequence: if another package collision occurs, the user sees the actionable cause instead of a misleading output symptom.

Reject incompatible release bundles before publishing

Add a release check that imports the bundled NumPy code, verifies the exact expected version, and fails the build if it differs. Add a regression test where old and new version records coexist but the loaded code is incompatible.

Consequence: this failure is caught in the release job and in the updater-overwrite scenario before users receive it.

Repair choice

Recommended: fix and release together

Repair the current installed runtime, pin NumPy 2.4.4 in the bundle and both setup modes, add the real import probe, and add the release guard. Then test separation once on GPU and once in CPU mode.

This fixes today's installation and prevents the next silent update from restoring the problem.

Temporary recovery only

Force-reinstall NumPy 2.4.4 in the installed app and remove the extra NumPy version records.

Separation should work immediately, but another release built with unconstrained NumPy can overwrite it again.

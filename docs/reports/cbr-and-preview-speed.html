Bitrate control everywhere, and a speed dial for the scene grid

What each change does, what you'd see differently, and one thing you probably have wrong about the current app.

1 Bitrate control on every export format Half a day

⚠ Your premise is slightly off — and it changes the fix

You said CBR is only available for H.264 10-bit CPU. What's actually true: the app already supports CBR on two formats — H.264 10-bit CPU and H.264 10-bit NVENC. The GPU one is hidden from you unless clip extraction is switched to GPU mode and your machine reports NVENC support. So on a normal CPU-mode session, the 10-bit CPU preset is the only one left standing that shows the control — which is exactly what you observed.

Why this matters: the encoder-side work for CBR is already written and tested. The change is mostly widening a gate, not building a feature. That's why this one is cheap.

What the three modes actually do to your file

Qualitysize varies

Every scene looks equally good. Busy action scenes eat far more data than a still shot. You can't predict the file size.

VBRsize ≈ target

Averages out to your number over the whole clip. Hard scenes still borrow extra. Lands near the size you asked for, not exactly on it.

CBRsize is fixed

Holds the same data rate start to finish. Duration × bitrate = file size, reliably. Calm scenes waste a little; hard scenes get squeezed.

You picked "practical CBR" — target rate, hard ceiling, fixed buffer. That's what every tool means when it says CBR, and it's already what the existing 10-bit path emits. Nothing changes about how CBR behaves; it just becomes reachable from more formats.

Three details worth your attention

  • Defaults per format, not one number for all. 20 Mbps is sane for H.264 and roughly double what AV1 needs for the same look. Each format remembers its own bitrate, so switching between them doesn't hand you a silly number.
  • The GPU-to-CPU rescue keeps your setting. When a GPU export fails, the app quietly retries on the processor. Right now some of those retries drop your bitrate choice and fall back to quality mode — so you'd ask for a 20 Mbps file and get an unpredictable one with no warning. That gets fixed as part of this.
  • None of these settings survive leaving the page. Export format, mode and bitrate all reset to ProRes LT / Quality / 20 every time the clip panel remounts. That's true today and this change doesn't fix it — persisting them is its own decision (do they belong in app settings? per-project?). Flagging it, not silently bundling it in.

2 Speed dial for the scene grid One to two days

A single setting that makes the scene tiles play faster or slower while you're browsing. It touches nothing you export.

Confirmed scope: grid tiles only. The big scene viewer keeps playing at normal speed, and exported clips are byte-for-byte identical to what you'd get today. The control lives in the tool column on the left of the clip page and in app Settings — same setting, both places stay in sync.

Why this is easy in the mode you're actually using

Your scene tiles are real video players — the same kind a browser uses to play any video. Telling a video player "run at 1.5×" is one line. The app just never asked.

There is a second, older preview mode that bakes each tile into a looping animated image at a fixed 12 frames per second. It's off by default. In that mode speed is physically impossible — an animated image has no playback control, and the only alternative is re-baking every preview on disk each time you nudge the slider.

Range: 0.25× to 4×

Not an arbitrary pick. Below a quarter speed and above four times, browsers start refusing the request outright rather than clamping it. Staying inside that window means the slider never silently does nothing at the ends. Snap points at 0.5×, 1× and 2× because those are the ones you'll actually reach for.

Two things that would break if handled naively

  • Slow motion would loop early. Each tile plays a slice of a longer file and jumps back to the start when it hits the end of the scene. There's a backup timer that computes "the scene ends in 800 milliseconds, snap back then" — and it assumes normal speed. At half speed the scene actually needs 1600 ms, so the tile would cut off halfway and restart. Symptom you'd notice: at 0.5× every tile plays only the first half of its scene. The timer has to be scaled by the speed.
  • Dragging the slider would restart every tile. The obvious implementation makes the whole playback loop rebuild whenever speed changes, which yanks every visible tile back to frame one. With a dozen tiles on screen, dragging from 1× to 2× would look like the grid stuttering and resetting. The speed change has to be applied to the already-playing videos rather than rebuilding them.
  • Two nearly identical playback engines exist — one for normal scenes, one for merged scenes stitched from separate pieces. They were deliberately kept as copies. Both need the same change, and the merged one has no tests at all right now, so the spec adds some.

What is deliberately not touched

  • Exports. A 2× setting does not produce sped-up files. If you ever want that, it's a different feature with its own audio question.
  • The scene viewer modal. It has a scrub bar and a time readout that would start lying if playback ran at 2×.
  • The behind-the-scenes lightweight copy the previews play from. It's built as a straight full-length copy specifically so its timeline lines up exactly with the original — that's what makes scene boundaries land correctly. Baking speed into it would shift every scene marker in the project, and it wouldn't help anyway since many sources play directly from the original file with no copy involved.

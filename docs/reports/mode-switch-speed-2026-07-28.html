Making the CPU ↔ GPU switch faster

What's actually left to win now that the fast installer is in — measured on your machine, 28 July 2026.

Short answer: yes, and the biggest one is free.

Now that packages install in seconds instead of minutes, the installing isn't the slow part any more — the checking is. Every switch re-asks the same health questions up to five times, each one starting a fresh Python just to answer, and the trip back to GPU re-runs a 70-package install for one missing file.

Four changes cut roughly 12–18 seconds off a switch and change nothing about the result. A fifth, bigger change would make the switch near-instant — and costs no extra disk space, which surprised me too.

The four free wins

1
biggest win

Stop reinstalling the entire audio stack to get one missing file

When you switch to CPU, the app removes the GPU version of the sound-separation runtime. When you switch back, it notices that file is gone — and reacts by reinstalling everything: the sound separator, the video reader, the scene detector, and twenty supporting libraries, with blanket permission to upgrade all of them.

What you'd see: a switch back to GPU that spends six seconds thinking before it starts, and occasionally much longer, because any one of those 70 packages having a newer release means a real download you never asked for.

The fix: when the only thing missing is the GPU sound runtime, install just the GPU sound runtime. The full stack install still runs when the stack is genuinely missing. The end state on disk is identical either way — I verified both routes produce the same package set.

Saves 4+ seconds every time, and removes the risk of an unwanted multi-package upgrade mid-switch
2
easy

Stop asking the same health question five times

There's a check that confirms the two number-crunching libraries the audio engine sits on still load together. It's a good check — it exists because an unrelated install once quietly broke that pair and the switch reported success on a dead engine.

But it fires five times per switch, and three of those five happen back to back with nothing installed in between. Each one starts a fresh Python from scratch.

The fix: ask once before anything installs, and once after the last install. Keep the answer in between. The protection is unchanged — the whole point of the after-check is to catch damage done during the run, and that still happens.

Saves 1.5–4.5 seconds
3
easy

Ask for the build you want by name instead of forcing a reinstall

Today the switch says "replace PyTorch, I don't care what's there". That phrasing has a hidden cost: it also tells the installer to throw away everything it remembers about PyTorch and re-check the download site from scratch.

If instead we name the exact build — "the CPU one" or "the graphics-card one" — the installer sees the installed build doesn't match and swaps it anyway, using what it already knows.

Measured: planning the swap drops from 2.5 s to 0.8 s, and the swap it plans is byte-for-byte the same one.

Careful bit: the forced-reinstall phrasing must stay on the repair path, where the point is to overwrite files that are damaged even though the records look correct. Only the plain mode switch changes.

Saves ~1.7 seconds and one unnecessary trip to the network
4
easy

Don't take the same inventory three times

The Settings panel takes an inventory to show you what it's about to do. The switch then immediately takes the identical inventory again before starting, and a third time at the end. On the GPU side each one costs 2.7 seconds, almost entirely spent loading PyTorch in a throwaway process to confirm the video reader can still start.

The fix: the middle one can reuse the panel's answer when nothing has been installed since. The final one has to stay — it's what catches a switch that half-worked.

Saves ~2.7 seconds on GPU switches

The fifth option: make it instant

Everything above shaves a switch that still fundamentally works by uninstalling one thing and installing another. There's a way to stop doing that at all.

Today

One package folder. Switching means tearing out the CPU build and laying down the GPU build, then re-verifying everything.

~40–60 seconds

→
Instead

Two package folders, one per mode, both ready. Switching means pointing Python at the other folder.

under a second

The part that makes this viable: it costs no extra disk

The fast installer doesn't copy files into your Python folder — it points at a single stored copy. I checked the actual link counts on your machine: the GPU PyTorch files in your Python folder and the ones in the store are the same bytes on disk, not two copies.

Already on your disk right now

  • GPU build of PyTorch — 4.37 GB, in use
  • CPU build of PyTorch — 0.43 GB, sitting in the store from your last switch

Both builds are already there. Both are already complete.

Cost of a second, ready-to-go folder

~0 GB extra

The second folder points at the same stored bytes. Windows Explorer will report the sizes twice, but the drive only holds one copy.

Honest about the cost: this is the only item on the page that isn't a small edit. It changes where packages get installed and how the app decides which folder Python reads. That means the setup screen, the repair paths, and the first-install flow all need to learn about two folders instead of one — and the mode-specific packages (PyTorch, the two sound runtimes, the video reader) have to live in the mode folder while everything shared stays put. It's worth doing as its own piece of work with a proper plan, not bolted onto the four fixes above.

What I'd deliberately not do

Merging the PyTorch step and the sound-runtime step into one command

It looks like an easy saving — two commands become one, and you skip a round of planning. But PyTorch comes from its own download site and the sound runtime comes from the public one, and combining them means telling the installer to consider both sites for everything. That's exactly how a previous switch quietly downgraded an unrelated library to whatever version PyTorch's site happened to be carrying. The two-second saving isn't worth reopening that.

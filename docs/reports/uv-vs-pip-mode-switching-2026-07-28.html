PyTorch's CPU build is roughly 500 MB unpacked. The CUDA build is several times bigger, so the gap on a real GPU switch is larger than what you see here, not smaller.

Why it's faster — the actual reason

It is not a faster download. It's that pip throws away its work and uv doesn't.

Today (pip) — every switch

1 · Fetch
Pulls the package archive. pip does keep the compressed archive, so this part is quick the second time.
fast
2 · Unpack
Unzips ~500 MB of files and writes every one of them into the app's Python folder. Redone from scratch every time.
the 80 seconds
3 · Discard
When you switch back, all those unpacked files are deleted and step 2 happens all over again.
wasted

With uv

1 · Fetch
Same download, but done in parallel across packages.
fast
2 · Unpack once
Unzips into its own storage area, once, ever, and keeps it there.
one time
3 · Point at it
Instead of copying 500 MB into the app's Python folder, it creates pointers to the files it already unpacked. Windows treats them as real files.
seconds

I confirmed those pointers are real: a 265 MB PyTorch file inside the test folder is the same file as the one in uv's storage, counted twice. It costs no extra disk, and Python loads it normally.

What that means when you switch modes. The first time you go to GPU it downloads and unpacks the CUDA build. Switch to CPU, then back to GPU — the CUDA build is still sitting unpacked in uv's storage, so "switching back" is just repointing. Roughly six seconds instead of a minute and a half.

What could break — and what I actually checked

Could uv refuse to install into the app's stripped-down Python?

Tested — no problem

The app doesn't use a normal Python setup; it ships a minimal Python folder and treats that as the environment. Some tools reject that. uv installed into it on the first try, put the files exactly where the app expects them, and the app's Python imported them.

Could uv reject your package list as unsatisfiable?

Tested — identical outcome to pip

This was my main worry: uv is stricter about conflicting requirements than pip, so a list pip tolerates can be refused outright. I ran both your GPU list and your CPU list — every package, exact same pins — through uv and through pip without installing, and compared. Both tools picked the same versions of everything. No refusals.

Something is already wrong here, and it isn't uv's fault

Found while testing Pre-existing

Your GPU setup runs two steps in order: first it installs the exact PyTorch build you pinned (2.11.0 with CUDA), then it installs the audio packages. That second step replaces your pinned PyTorch with a generic 2.13.0 from the public package index — no CUDA, wrong version. Both pip and uv do this, so it's happening today.

If it fires, the symptom is: setup finishes, then the settings screen immediately tells you PyTorch needs installing again, and the GPU clip engine can't load because it's built against 2.11 specifically. Your right-now installed state is correct (2.11.0+cu128), so either you haven't hit it or something re-fixes it — but the ordering makes it possible on any run.

Worth fixing separately, either by pinning PyTorch in the audio step too, or by reinstalling the pinned build last. I did not change anything.

Shipping it to real users

Costs nothing if done this way

uv is a single 76 MB program (26 MB compressed). Putting it in the installer grows every download by 26 MB.

You already have a better route. The app downloads FFmpeg and yt-dlp on demand into a per-user tools folder, driven by a list at C:\projects (code)\27. Ultimate AMV script\tools.json That list already supports "fetch a zip, pull one file out of it, verify the checksum, and don't download it until it's needed" — which is precisely what uv needs. Adding uv there means zero growth to the installer, and it only downloads the first time someone opens setup.

Should it ship, or is it just a dev tool?

It should ship. But it should not replace pip — it should sit in front of it.

What a real user gets

  • First-run setup roughly halves. That run downloads and unpacks several gigabytes — PyTorch, the audio stack, a graphics runtime. It's the single most painful moment in the whole app, and it's the one moment every user hits.
  • Costs them about 20 MB of disk, not gigabytes.
  • Nothing extra to download at install time, if it goes in the tools list.
  • It doesn't need a working Python to run. Today, if the app's Python installation gets damaged, the repair path is to download a pip installer and run it with that same damaged Python. uv is a standalone program, so it can repair an environment that can't currently repair itself.

Why pip still stays in the box

  • pip is 13 MB of the shipped Python folder. Removing it saves nothing worth having.
  • uv arrives by download. Downloads get blocked — corporate networks, overzealous antivirus, GitHub being unreachable. If that's the only installer, a blocked download means setup simply cannot proceed, with no way out.
  • With pip still present, that same user gets the slow path instead of a dead end, and you get a log line telling you it happened.
  • It also means you can roll this out without a hard cutover — the two tools read and write the same records, so a half-migrated machine is still a working machine.

One thing to decide alongside it. Over months, uv's storage accumulates versions nobody uses any more — an old PyTorch from three releases ago stays on disk forever. uv can drop exactly the unused ones on command. That should run quietly after a successful setup, with nothing shown to the user and nothing they still need ever touched.

uv reads its own settings files; pip did not

Guard against it

Your rule is that the app never picks anything up from the wider system — it only ever uses its own bundled pieces. Today that's enforced by a flag that seals pip off. uv has its own settings files and environment variables that could redirect where packages come from on a machine that happens to have them. There's a flag (--no-config) that seals it the same way; it just has to be on every command from day one.

Does a failed download leave you with nothing?

Expected safe One test I'd still run

You deliberately install-over rather than remove-then-install, so a network drop mid-switch leaves the previous working version in place instead of an empty hole. uv downloads and unpacks everything before it touches the installed folder, so this should hold or improve. I did not simulate a mid-install network failure — it's worth one deliberate test before you trust it in a release.

Do the two tools fight if both are used?

Tested — they coexist

Packages installed by uv are fully visible to pip and vice versa. So you can move over gradually and keep pip as a fallback path rather than doing a hard cutover.

What I'd recommend

  1. Fetch uv the same way you fetch FFmpeg Add it to the tools list, marked as "only download when needed". Installer size unchanged, users only pay for it when they open setup.
  2. Route every install through one place Right now the command text is spelled out in five separate spots. Funnel them through a single builder that decides uv-or-pip. That is what makes the fallback possible and makes the change small.
  3. Keep pip as an automatic fallback, not a permanent second path If uv is missing or fails to start, fall back to the current pip command and log it. Users never see a hard failure; you get a signal if uv ever misbehaves in the wild.
  4. Stop asking pip whether a package is installed Six of these checks run every time the setup screen opens, each starting a fresh Python process. Reading Python's own package records instead is instant and works no matter which tool installed it.
  5. Fix the PyTorch-gets-replaced problem separately, first It's independent of this change and it is the kind of thing that would get blamed on uv if it surfaced right after the switch.
  6. Then measure a real GPU↔CPU round trip My numbers are the CPU PyTorch build in isolation. The full switch also moves the audio stack and the two graphics runtimes. Same mechanism applies, but I'd rather show you the real number than promise one.

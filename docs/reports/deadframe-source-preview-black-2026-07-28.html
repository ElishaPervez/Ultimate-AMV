Your Scene Splitter already solved exactly this

The Scene Splitter checks each file first, and when it finds one the interface can't show, it quietly builds a small, low-resolution stand-in copy in a format that plays, then previews that instead. You'd never notice it happened. Two ready-made pieces already exist for this — one that inspects a file and answers "playable, or does it need a stand-in?", and one that builds the stand-in. Dead Frame Remover simply never got wired to them. (src-tauri/src/clips.rs — the playback-plan and proxy-builder commands, already registered app-wide.)

04A second bug I predicted here — and was wrong about

Correction to an earlier draft of this report

I originally wrote that picking ProRes · MOV as the output would make the right-hand window go black too. That was wrong. I checked the code that actually builds the preview and it never touches your format choice.

The Preview button always writes a small, fast, always-playable file, no matter which output format button is lit. Your format choice only applies when you press Export. That is a deliberate decision someone made when building this panel, and a good one for a reason worth knowing:

Why the preview ignores your export settings

The preview exists to answer one question — did the sensitivity dial pick the right frames? — and nothing else. Because it never depends on the format or quality settings, changing those doesn't invalidate the preview you're already looking at. You can dial in sensitivity, then choose your export format afterwards, without re-rendering.

So only the left-hand Source window was ever black. The right-hand one was always fine.

06Three ways to fix it

RECOMMENDED

A · Reuse the stand-in preview the Scene Splitter already uses

Check the file first. If the interface can't show it, quietly build a small playable copy and preview that.

Today

  1. Panel takes the file path
  2. Hands it straight to the player
  3. Player can't decode it
  4. Black rectangle, no explanation

With this fix

  1. Panel takes the file path
  2. Asks: can the interface show this?
  3. If not, builds a small playable copy (a second or two)
  4. Preview plays normally — you never know it happened
In its favour
  • The machinery already exists, is registered, and is proven in the Scene Splitter
  • Fixes every unplayable format at once, not just ProRes — MKV, 10-bit, odd codecs
  • Both windows go through the same check, so the result player is protected if that encoder ever changes
  • Nothing new for you to learn or click
The cost
  • A short wait before an unplayable clip appears, with a progress state to show
  • Stand-in copies take temporary disk space and need cleaning up
  • The preview is lower resolution than the original — fine for spotting duplicate frames, not for judging fine detail
Scope: Dead Frame Remover panel only. Both windows. No backend work — the backend pieces exist.

B · Just say so

Detect the unplayable file and replace the black rectangle with a clear message plus an "Open in your video player" button.

In its favour
  • Smallest possible change
  • No waiting, no temporary files, no disk use
  • Honest — never leaves you staring at a black box wondering
The cost
  • You still can't preview inside the app, which is the whole point of the panel
  • Comparing before/after side by side becomes impossible for these files
  • Feels like an apology rather than a feature
Scope: One panel, cosmetic. Good as a stopgap, or as the fallback when building a stand-in fails.

C · Do both — stand-in preview, with the message as a safety net

Option A normally; if building the stand-in fails or the file is enormous, fall back to Option B's message.

In its favour
  • Never shows a black rectangle under any circumstances
  • Handles the case where a huge source would take too long to convert
  • Covers corrupt or half-written files gracefully
The cost
  • Two code paths to keep working instead of one
  • Slightly more to test
Scope: Option A plus a small failure branch. This is where I'd expect to end up eventually.

07The separate, smaller problem: that grey bar

Even after the picture works, the player will still look wrong. That dark grey bar with the three-dot menu is the browser engine's built-in control bar — the app is asking for default controls rather than drawing its own.

Your Tsukyio player and Scene Viewer both hide the default bar and draw a matching custom transport instead. The Dead Frame Remover asks for the default one, so it gets stock Chrome chrome, complete with a "⋮" menu offering things like Picture-in-Picture and Download that don't belong in your app. (src/features/deadframe/DeadFramePanel.tsx:561 and :576.)

Worth deciding separately

This is purely cosmetic and independent of the black-screen bug. Two side-by-side windows comparing before and after would also benefit from a shared transport — one play button scrubbing both at once — which is a genuinely better fit for this panel than two unlinked players. Say the word and I'll spec that on its own.

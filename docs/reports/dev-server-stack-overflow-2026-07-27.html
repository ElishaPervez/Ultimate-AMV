Your dev server dies before a single line of Rust gets compiled

27 July 2026 · diagnosis confirmed by measurement, not inference · one folder is responsible

What you see: you run npm run tauri dev, it prints thousands of file paths, then thread 'main' has overflowed its stack and quits. The window never opens.

What is actually happening: installing the audio-separation tools dropped 3,825 empty folders into your bundled Python. Every time you start the app, Tauri walks that whole Python folder to copy it into the app. Its walker takes one step deeper into itself for each empty folder it passes and only unwinds when it finally finds a real file. It hits 3,771 empty folders in a row, runs out of room to keep track of where it was, and the crash kills the whole startup.

The chain, start to crash

1
The app ships its own Python, and Tauri copies it on every start Your build config lists the python and backend folders as things to bundle into the app. Before Rust compiles, Tauri walks every file in them, prints it, and copies it. That is the flood of rerun-if-changed=..\python\... lines you saw — 25,148 files, all normal.
2
Audio separation needed onnx, and onnx ships its own test scaffolding The stem-splitting feature pulls in a model-conversion library, which pulls in onnx. That package includes a folder tree of test fixtures. In the version that got installed, the fixture folders are all there but the fixture files are not — 3,825 directories holding 9 small text files between them, all under python/Lib/site-packages/onnx/backend/test/data.
3
Tauri's folder walker digs into itself once per empty folder The walker's job is to hand back the next file. When the next thing it sees is a folder, it doesn't loop — it calls itself again to ask for the next thing, and stays paused waiting for the answer. Ten folders in a row means ten paused calls stacked up. A few thousand in a row means a few thousand, all still waiting. The pile only collapses once a real file turns up.
4
The pile hits the wall at ~3,771 deep and the process is killed outright Each paused call needs a slice of a fixed 1 MB scratch area. Around 3,771 of them, the area is full and Windows kills the process on the spot — exit code 0xc00000fd, "stack overflow". Because this is the pre-compile step, nothing downstream runs: no Rust build, no window, no dev server.

Everywhere else in the bundled Python the deepest run of back-to-back folders is 5. Only this one tree goes into the thousands.

How I know it's this and nothing else

I re-ran Tauri's walking order over your actual Python folder and measured the longest run of consecutive folders, first as-is, then pretending the onnx fixture tree was gone:

as it stands now      →  3,771 folders in a row   (last one: onnx/backend/test/data/real/test_bvlc_alexnet)
with that tree gone   →      5 folders in a row   (deepest spot: a numpy license folder)
Crash point matches: the final line your terminal printed was onnx/backend/test/cmd_tools.py — the last real file immediately before that fixture tree.
Not a Tauri version problem: the newest Tauri build tooling on your machine (2.9.2) has the exact same self-calling walker. Upgrading does not help.
Not your code: nothing in this repo changed. Only the contents of the bundled Python folder did.

What's in the folder I want to delete

ItemContentsUsed at runtime?
onnx/backend/test/data/ 3,825 folders, 9 files (1.1 MB). The 9 files are small pointers listing download URLs for public test models — AlexNet, ResNet50, VGG19 and friends. No Fixtures for onnx's own test suite. Nothing your app does touches them; the app never runs onnx's tests.
onnx/backend/test/case/, runner/, report/ Real Python code, ~700 files, importable. Leave alone Harmless, and shallow enough that it never triggers the crash. No reason to touch it.

If it were ever needed, one pip install --force-reinstall onnx-weekly brings it straight back. Nothing is unrecoverable here.

Ways to fix it

A · Delete that fixture tree, then teach the installer to delete it too recommended

Two parts. First, remove the folder now — your dev server starts again within seconds. Second, add a cleanup step where the audio tools get installed, so the next person (or the next reinstall on your own machine) doesn't hit the same wall.

  • Unblocks you immediately.
  • Survives reinstalling the audio dependencies.
  • Also trims 3,825 pointless folders out of the shipped installer, which speeds up packaging.
  • Nothing about how the app runs changes.

B · Delete the folder and nothing else

Fastest possible move, no code change.

  • Works today.
  • Comes back the moment audio dependencies are reinstalled or a fresh machine sets up — and the crash message gives no hint what caused it, so you'd lose another hour rediscovering this.

C · Stop bundling the whole Python folder wholesale

List narrower paths instead of the entire python folder, so 25,148 files aren't walked and re-copied on every single start.

  • Would genuinely speed up every dev start and every build.
  • Risky to do casually — miss one path and the app ships a Python that can't import something, which only shows up when a user clicks the feature that needs it. Worth doing deliberately later, not as a crash fix.

D · Report it upstream to Tauri

Their walker should loop instead of calling itself; then no number of empty folders could ever break it.

  • Correct long-term, but it does nothing for you this week.
  • Worth filing alongside whichever fix you pick.

How to check it's fixed

Run npm run tauri dev again. You should still see the long flood of file paths — that part is normal and unchanged — but it now runs to the end, Rust starts compiling, and the window opens. If it crashes at the same spot with the folder gone, the diagnosis was wrong and I'll dig again; the measurement above says it won't.
